# 0.4.0 development plan

PS2 Memory Card Inspector 0.4.0 starts from the hardware-tested `0.3.0-dev5` diagnostic frontend and expands it in three directions: configurable display/output, deeper card verification, and a verified FreeMcBoot installation transaction built on the modern PS2SDK 2.0 security stack.

## Milestone 0 — configurable GS frontend

The 0.3 frontend deliberately exposed one native 640x224 FIELD presentation while its mechanics were being validated. The updated `fhdb-bootstrap-manager` 0.4.3 renderer has since established a safer runtime mode-switching model, so 0.4 ports that architecture rather than inventing another one.

The logical Inspector layout remains 640x224. Runtime output may select:

- Native;
- 480p;
- 576p;
- 720p;
- 1080i.

The user-facing labels intentionally do not repeat `progressive` or `interlaced`: the `p`/`i` suffix already encodes scan type, and concise labels stay readable inside the Settings value column.

The renderer keeps native output as the recovery baseline, reserves alternate VRAM separately, maps the logical UI through a pixel-snapped viewport, uses bounded GIF/VSync waits, and restores native output after a failed transition. The 576p compatibility path and explicit HDTV display windows follow the hardware-tested HDD-manager implementation.

A fourth `SETTINGS` page exposes display mode and diagnostic/install policy without conflating settings navigation with memory-card slot selection.

Settings overflow behavior is accessibility-oriented:

- only the currently selected setting may animate overflowing value/help text;
- non-selected rows remain static;
- marquee motion is right-to-left at one 8-pixel glyph every 480 ms;
- the selected text pauses at its beginning before scrolling;
- changing the selected row or changing a setting value restarts the marquee from the beginning.

## Milestone 1 — deeper filesystem verification

The disposable card integrity test becomes selectable:

- Quick: 4 KiB;
- Extended: 64 KiB;
- Thorough: 256 KiB.

All profiles stream deterministic 4 KiB chunks. They retain the same write -> flush -> close -> reopen -> read -> compare -> delete -> verify-delete boundary while avoiding a large EE allocation. This is still a disposable test file and never overwrites an existing card file.

## Milestone 2 — installer transaction engine

The installer must not be a blind copy loop. A normal FMCB install is represented as an explicit transaction whose stages are reportable in the GS progress UI.

Required sequence:

```text
validate diagnostics/preconditions
  -> resolve console ROM/region and exact destination names
  -> build complete source/destination manifest
  -> calculate required target space
  -> inventory existing destination state
  -> capture rollback data for every target that will be replaced
  -> bind every KELF in RAM using PS2SDK 2.0 SECRMAN 1.4
  -> restore the normal Sony ROM X card personality
  -> create required directories/attributes
  -> write each file
  -> flush + close
  -> apply selected read-back policy
  -> commit only after the selected policy succeeds
  -> rollback touched targets on any failure
```

Read-back policy is user-selectable:

- `ENFORCED` — default and recommended; reopen and byte-compare every selected file;
- `REQUIRED ONLY` — fully verify required files while optional payloads skip the second read;
- `DISABLED` — skip destination read-back, retain persistent USB rollback protection, and explicitly report the install as unverified.

The project will initially implement the normal console-region installation path. Cross-model/cross-region/multi-install semantics remain a later milestone because they require memory-card page/crosslink behavior that must not be approximated with ordinary file copies.

## Milestone 3 — package completeness

The normal installer should understand the actual FMCB package structure rather than only the minimum preflight subset:

- `SYSTEM/FMCB.XLF` as the card-bound OSDSYS update payload;
- `SYSTEM/ENDVDPL.XRX` as a card-bound KELF;
- region-specific `SYSTEM/B?ICON.SYS` plus `SYSTEM/FMCB.ICN`;
- `SYS-CONF/FMCB_CFG.ELF`, `FREEMCB.CNF`, icon resources and USB modules;
- optional recursive `BOOT` and `APPS` payloads when present.

ROM versions older than 1.30 require the legacy `osdXXX.elf` destination naming used by FreeMcBoot. ROM 1.00/1.01 use `osd130.elf`.

Existing `FREEMCB.CNF` preservation is a user-facing policy. Release defaults keep full `ENFORCED` read-back verification even though advanced users may explicitly choose a weaker policy.

## Milestone 4 — install/update/uninstall lifecycle

After normal installation survives physical testing, add explicit handling of:

- an existing FMCB installation;
- upgrade while preserving user configuration;
- uninstall metadata written by this project;
- rollback after a failed update;
- import/recognition of legacy FMCB uninstall metadata where practical.

Do not delete unknown files merely because they live in a directory used by FMCB.

## Milestone 5 — cross-model / multi-install research

Reference FreeMcBoot uses page-level/crosslink operations for cross-model and multi-install behavior. These modes are out of scope for the first 0.4 installer candidate until an equivalent PS2SDK 2.0 implementation is understood and independently validated.

## Regression requirements

Every installer-capable build must retain the established diagnostic matrix:

- Sony 8 MB positive-control card A;
- Sony 8 MB positive-control card B;
- third-party 64 MB card with functional MagicGate/CardAuth;
- third-party 64 MB card without functional MagicGate/CardAuth.

The no-MagicGate card must remain filesystem-testable and must be rejected before any KELF installation write.

Display-mode work must never alter the IOP/card architecture. MagicGate remains isolated from ordinary ROM X filesystem I/O, and a security session must restore the normal environment before any destination file is written.

GUI regression testing must include repeated `720p -> 1080i -> 720p` transitions with no font-atlas corruption and a Settings test confirming that only the highlighted overflowing row moves at the 480 ms/glyph marquee rate.
