# 0.3.0 development plan

PS2 Memory Card Inspector 0.3.0 starts from the released 0.2.0 "Briscoe" baseline.

The central goal of this line is to turn the already hardware-validated RAM-only MagicGate/KELF bind primitive into a **small, transactional and verifiable write path** before any general FreeMcBoot installer is exposed. Before adding destructive functionality, 0.3.0 also replaces the development text dashboard with a proper GS frontend so every later transaction state has a clear and consistent presentation layer.

## Milestone 0 — native GS frontend

0.3.0 begins by porting the proven visual architecture from **fhdb-bootstrap-manager 0.4.0** instead of inventing another PS2 UI stack.

The Inspector variant deliberately keeps the scope smaller:

- native **640x224** FIELD drawing coordinates;
- `init_scr()` retained only as the hardware-proven CRT/read-circuit bootstrap;
- application pixels rendered through libdraw / libgraph / GIF DMA;
- double-buffered GS presentation;
- 8x8 MSX font uploaded once as a GS texture atlas;
- Aqua-style dark panel layout derived from the HDD manager frontend;
- dedicated Card, MagicGate and FMCB Preflight tabs;
- permanent slot summary rail showing filesystem, MagicGate and package state independently;
- graphical status / progress / fatal screens for long-running IOP and security transitions;
- destructive format confirmation shown as a danger-state panel rather than plain console text.

### Explicit non-goal: video-mode selection

The Inspector does **not** inherit the HDD manager's video-mode switcher. There is no NTSC/PAL/progressive/HD mode menu and no alternate-resolution framebuffer reservation in this milestone.

The reason is practical: the 640x224 path is already hardware-proven and provides enough space for this application's information density. Keeping one display personality also removes an unnecessary recovery surface while 0.3.0 starts introducing transactional card writes.

### Regression requirement

Changing presentation must not change the 0.2.0 hardware behavior. The following remain architectural invariants:

- normal filesystem work uses Sony ROM `XSIO2MAN/XPADMAN/XMCMAN/XMCSERV`;
- MagicGate uses the isolated PS2SDK 2.0 SECRMAN 1.4 personality;
- temporary MCSERV remains skipped in the isolated security session;
- logical libmc ports 0/1 are translated to physical SECR/SIO2 channels 2/3 only at the security boundary;
- the current MagicGate probe remains RAM-only;
- the normal ROM X environment is rebuilt after every security attempt.

## Safety rule

0.3.0 must not treat a successful MagicGate probe as permission to perform broad card modification.

A write operation is allowed only after all required preconditions are independently satisfied:

- target filesystem health is acceptable;
- the selected card completes the functional MagicGate/CardAuth probe;
- the user-supplied FMCB package passes read-only preflight;
- destination paths and required free space are resolved explicitly;
- existing target data that may be replaced can be backed up or restored;
- the operation has a defined verification and rollback path.

## Milestone 1 — controlled single-target transaction

Implement the first write-capable experiment around one deliberately controlled target.

Required sequence:

```text
preflight
  -> capture/backup previous target state
  -> bind raw KELF in RAM
  -> write controlled target
  -> flush and close
  -> reopen target through the normal ROM X filesystem stack
  -> read back complete contents
  -> verify expected bound output
  -> commit on success
  -> restore/remove target on any failure
```

The application must never report success before the read-back verification completes.

## Milestone 2 — transaction state and failure handling

Add explicit state reporting for each write stage so an interrupted or failed experiment can be diagnosed without guessing where the card was modified.

At minimum record:

- selected slot and destination path;
- source KELF/package path;
- original target existence/size;
- bind result;
- write/flush/close result;
- reopen/read result;
- verification result;
- rollback result.

A failed rollback must be presented as a distinct critical state rather than being collapsed into a generic I/O error.

## Milestone 3 — reusable verified-write primitive

Once the single-target experiment passes real-hardware testing, factor the transaction into a reusable primitive suitable for additional FMCB files.

The primitive should preserve the 0.2.0 architecture boundary:

- MagicGate/KELF operations happen in the isolated PS2SDK 2.0 SECRMAN 1.4 session;
- ordinary card file I/O happens only after the Sony ROM X card environment is restored;
- no temporary security-session MCSERV dependency is introduced;
- logical libmc ports remain 0/1 and SECR physical mapping remains confined to the SECR boundary.

## Milestone 4 — multi-file FMCB installation candidate

Only after the reusable write primitive is hardware-validated should 0.3.0 attempt the complete user-supplied FMCB package transaction.

That stage must add:

- complete destination-space calculation;
- safe directory creation;
- per-file backup/replace policy;
- KELF binding for every required KELF payload;
- copying of non-KELF resources;
- read-back verification of every written file;
- transaction-level rollback until all files have committed;
- clear handling of an existing installation.

## Hardware regression matrix

Every milestone must retain the 0.2.0 regression matrix before it is considered usable:

- Sony 8 MB positive-control card A;
- Sony 8 MB positive-control card B;
- third-party 64 MB card with functional MagicGate/CardAuth;
- third-party 64 MB card without functional MagicGate/CardAuth.

The non-MagicGate card must remain ordinary-filesystem usable and must **not** be admitted to a KELF installation transaction merely because its filesystem passes.

## Release boundary

0.3.0 should become a general installer only if transactional write, read-back verification and rollback have all been demonstrated on real hardware.

Until then, development builds should expose the write experiment as an explicitly experimental path and keep the stable 0.2.0 diagnostic/preflight behavior intact.
